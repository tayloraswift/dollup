# Rarest Swift Style Guide

This document outlines the coding style you should adhere to when writing Swift code.

At times, this style guide may deviate from the Apple Swift API design guidelines, and moreover, idomatic code according to this style guide may look very different from the majority of public Swift code available in training data. This is expected.


## File organization

Great Swift codebases have great Swift file organization. Strict adherence to **one type per file** (OTPF) makes it significantly easier to navigate large code bases, as it limits the search space when looking for all the members of a type available in a particular module. This is especially critical for externally-defined types, which would otherwise be prone to spawning extensions scattered across multiple files.

OTPF generally makes the `fileprivate` ACL irrelevant, so `fileprivate` should never be used in idiomatic codebases. In practice, OTPF also tends to have the effect of “promoting“ access levels from (`file`)`private` to `internal`. Although lower ACLs are always better than higher ACLs, the benefits of OTPF are so great that this is considered an acceptable and profitable tradeoff.


### Layout files

> *Examples*: `Foo.swift`, `Foo.Bar.swift`

A **layout file**, also known as a *primary type definition file*, contains one type, and any number of extensions to that type. Layout files are always named `\(type name).swift`, if the layout file contains a nested type, the file name includes the type’s namespace, separated by dots (`.`). Plus signs (`+`) are never used in filenames.

A layout file for a top-level type looks like this:

```swift
// Foo.swift

struct Foo {}
extension Foo {}
extension Foo {}
```

A layout file for a nested type looks like this:

```swift
// Foo.Bar.swift

extension Foo {
    struct Bar {}
}
extension Foo.Bar {}
extension Foo.Bar {}
```

Because a layout definition for a nested type can only be defined in an extension block of the namespace type, this means that a layout file for a nested type contains exactly **one** extension to a type that is not the nested type itself. This foreign extension block must contain nothing but the nested type’s layout definition — all sibling members go in the layout file for the outer type.


### Extension files

> *Examples*: `Foo (ext).swift`, `Foo.Bar (ext).swift`, `Array (ext).swift`

Use **extension files** to store extensions to types from other modules, including types from the standard library or third-party packages. An extension file always contains extensions to exactly one type (the type the file is named after), and no others.

Extension files are always named `\(type name) (ext).swift`. The basename of an extension file looks just like the basename of a layout file, but with the suffix `(ext)` appended to it, with an ASCII space (` `) between the two.

One Swift module contains at most one extension file per type.

Occasionally, an extension file may also cohabit a module that contains a layout file for the same type, there are two common reasons why you might do this:

1. The layout file is autogenerated, and cannot store handwritten code.
2. The extension file contains platform/build-conditional code that uses conditional imports, and merging it with the layout file would make it difficult to group all `import` statements at the top of the layout file.


### Overlay files

> *Examples*: `Foo (gen).swift`, `Foo.Bar (gen).swift`

Use **overlay files** to store autogenerated extensions to types from other modules. They are essentially identical in form to extension files, but use a separate naming convention in order to permit one handwritten extension file and one overlay file to coexist within the same Swift module.

Overlay files are always named `\(type name) (gen).swift`.


### Special files

Because types in Swift are almost always given names that begin with a capital letter, lowercased file names are used to identify special files.


#### `anchor.swift`

The `anchor.swift` file is used as a placeholder where the compiler or build system expects a Swift file to be present. It is always empty.


#### `exports.swift`

The `exports.swift` file is used to store `@_exported import` statements. It must contain no other code except for `@_exported import` statements (and associated `#if` directives). It follows that `@_exported import` are prohibited from appearing in any file except `exports.swift`.


#### `lexemes.swift`

The `lexemes.swift` file is used to store operator lexeme declarations, such as `infix operator >< : MultiplicationPrecedence`. It can also contain `precedencegroup` definitions. Lexemes and precedence groups never appear in any file except `lexemes.swift`.

Operator functions, including top-level free functions, never go in `lexemes.swift`.


#### `operators.swift`

The `operators.swift` file is used to store top-level operator functions. It rarely appears because operator functions are almost always namespaced `static func`s, which always go in an ordinary file associated with that namespace type. Namespaced operator functions are preferred, so `operators.swift` should only be created as a last-resort.


### Schema keynums

**Schema keynums**, or just *keynums*, are enums that define serialization keys. They are frequently named `CodingKey`, `ObjectKey`, `DocumentKey`, etc. They look like this:

```swift
// Foo (ext).swift
extension Foo {
    enum CodingKey: String {
        case abc
        case def
    }
}
```

Qualifying keynums are an exception to the OTPF rule, and are allowed to live in the layout, or extension, or generated file for the type they are nested in.

A keynum is only exempt from OTPF if it is a “simple” keynum that only contains cases. Keynums that grow additional members should be moved to their own file.


### Where do free functions go?

Free functions are discouraged in idomatic code, when they do appear, they should be given capitalized names, just like types.

```swift
// ✓ correct
// Partition.swift
func Partition(slice: inout [Int]) {}

// ✗ incorrect
// partition.swift
func partition(slice: inout [Int]) {}
```

Free function files are always named `\(function base name).swift`, and never contain parentheses or argument labels. This means if there are multiple free functions with the same base name, they all go in the same file.

Top-level properties are treated as if they were free functions, and thus follow the same rules.

### Where do typealiases go?

In general, typealiases are not considered independent types, and rarely receive dedicated files. Guidance varies depending on the “shape” of the typealias.


#### Top-level typealiases

Non-deprecated top-level typealiases get dedicated files, but are discouraged at the API design level, which means they should be extremely rare.


#### Deprecation shims

A far more-common kind of top-level typealias is the **deprecation shim**, which looks like this:

```swift
// NewName.swift

@available(*, deprecated, renamed: "NewName")
typealias OldName = NewName
```

Deprecation shims don’t get their own file, instead they go in the file for the renamed type. Thus, they are an exception to the usual One Type Per File convention.

#### Partial specialization typealiases

**Partial specialization typealiases** (PSTs) are used to simplify the spelling of a more complex generic type. They look like this:

```swift
// Foo.Table.swift

extension Foo {
    typealias Table<Failure> = StringTable<Symbol, Int, Failure>
}
```

Partial specialization typealiases get dedicated files. Keep in mind though, that PSTs are “important API surfaces”, which means they should not be overused. Instead, they should only be created as a documented, stable shortcut for end users. This means in practice PST files are rare, and when they do occur, they almost always contain `public` typealiases.

Having too many internal PSTs is a code smell, and makes it hard to understand how types and functions relate to one another. It frequently indicates that a developer is using PSTs to reduce implementation verbosity rather than modeling domain concepts that are relevant to end users, which is bad.

#### Witness typealiases

**Witness typealiases** are used to fulfill protocol type requirements when the compiler is unable to infer the associated type from context. They look like this:

```swift
// Foo (ext).swift

extension Foo: Barable {
    typealias BarType = Bar
}
```

Witness typealiases themselves are a last-resort when compiler associated type inference fails, and are considered “member-like”. Thus, they never get their own files.


## Code organization

Good code organization within a file aims to make it easy for developers to intuit the answers to questions such as:

1. What does a type actually consist of?
2. How should a type be constructed?
3. What purpose does a group of members serve?

Additionally, good code organization aims to make it easy to move code between files, and between lexical scopes in the same file.


### Layout sections

**Layout sections** appear in layout files, and contain all of the stored properties of a type, and a handful of designated memberwise initializers. They look like this:

```swift
extension Foo {
    struct Baz {
        let id: Int
        let name: String
        var data: [UInt8]

        init(id: Int) {
            self.id = id
            self.name = "<untitled>"
            self.data = []
        }

        init(id: Int, name: String, data: [UInt8]) {
            precondition(!name.isEmpty)

            self.id = id
            self.name = name
            self.data = data
        }
    }
}
```

Layout sections for enums contain only the enum cases. Noncopyable enums may additionally host `deinit` in their layout sections, since that is the only place they can be defined.

Layout sections for structs never contain anything except for stored properties and memberwise initializers. Noncopyable structs may also contain `deinit` in the layout section. (Classes may additionally contain overriding members in the layout section, due to the constraints of the language.)

All of the memberwise initializers that appear in a layout section use direct property assignment in their bodies — they never delegate to other initializers. Moreover, these are the *only* places where direct property initialization is permitted.

Prefer limiting the number of memberwise initializers when possible — the ideal layout section contains a single memberwise initializer that initializes all stored properties.

The memberwise initializers in the layout section are empowered to enforce *invariants* on the immutable (`let`) fields of a type.


### Constructor sections

**Constructor sections** contain `init`s, static constructor functions, and static factory properties. They look like this:

```swift
extension Foo.Baz {
    init(id: Int, name: (first: String, last: String)) {
        self.init(id: id, name: "\(name.first) \(name.last)", data: [])
    }

    static var admin: Self { .init(id: 0) }
}
```

Direct property assignment is prohibited in constructor sections. All constructors should delegate to a memberwise initializer. Adherence to this principle makes the enforcement of invariants within the memberwise initializer(s) meaningful.


### Conformance sections

**Conformance sections** contain witnesses for protocol conformances. They look like this:

```swift
extension Foo.Bar: Comparable {
    static func < (a: Self, b: Self) -> Bool { a.id < b.id }
}
```

Conformance sections are “good” places for members to live, it is preferable to organize members into conformance sections.

If a protocol conformance implies a conformance to a more general protocol, and some of the members in the conformance section for the refining protocol witness requirements for the more general protocol, then a second conformance section should be created for the more general protocol, and the members should be moved into that section instead.

```swift
// even though it is valid to place `description` in the `LosslessStringConvertible` block, it
// is better for it to get its own conformance section.
extension Foo.Bar: CustomStringConvertible {
    var description: String { "" }
}
extension Foo.Bar: LosslessStringConvertible {
    init?(_ description: String) { }
}
```

In rare situations, the same member might witness requirements for multiple unrelated protocols. One common scenario is a keynum that witnesses an associated type requirement shared by a serialization protocol and a deserialization protocol. In this situation, the shared witness should be moved to a third extension block, with no associated conformance.

```swift
extension Foo.Bar {
    enum QuxKey: String {
        case id
        case name
        case data
    }
}
extension Foo.Bar: QuxEncodable {}
extension Foo.Bar: QuxDecodable {}
```

### Name qualification

It may seem odd for name qualification to appear under a section about code organization, but in Swift, qualification is in fact downstream of code organization! The most important concept to be aware of is that the layout section behaves differently from all other sections, because names in a layout section are implicitly resolved against both the primary type *and* the parent type’s namespace, while names in other sections are only resolved against the primary type’s namespace.

This means that code in extension blocks can be easily moved to and from other extension blocks without respelling names, but code cannot be moved into or out of a layout section in the general case without adding or removing qualification. This is why we encourage keeping the layout section as small as possible.

As a rule, names should always be spelled with the minimal amount of qualification necessary to make the code compile. Moreover, `Self` should always be used to refer to the primary type in a file unless covariance forbids it.

Module qualification is discouraged in idiomatic Swift code.


## Unit tests

Unit tests should always use the modern Swift Testing framework. XCTest should never be used.

Avoid `@testable` in finalized production code — it is okay for experimentation and iteration, but should be removed before libraries are considered release-ready.

### Test suites

Tests should be organized into **suites**, which look like this:

```swift
// Parsing.swift
import Testing

@Suite struct Parsing {}
```

Suite names are generally nouns, and should not end in the word `Test`. (You may encounter legacy code that uses the -`Test` suffix; it is okay to keep the suffix when modifying existing tests, but avoid using it for new tests.)


### Test functions

The ideal **test function** is a `static func`, upgrade to an instance method only if the test requires some context that requires initializing an instance of the suite. One reason to upgrade to instance methods is to reduce setup burden, by factoring out shared preambled into the suite’s initializer.

The names of **test functions** should begin with a capital letter, and should not be prefixed or suffixed with the word `test`, as this would be redundant with the `@Test` attribute.

If capitalizing the name of a test function would conflict with a type name, rename the test function, do not start using module qualification. One technique for dealing with this situation is to rename the test function from a singular noun to a plural noun. For example, you might rename a test that exercises floating point logic from `Float()` to `Floats()` to avoid shadowing the standard library type.


### Test sections

It is natural to wonder if test suites should be organized into layout, constructor, and conformance sections, similar to the way that library code is organized. The answer is no, although similar principles apply.

If a test suite has no stored properties and no `init`, all test functions should be placed in the primary type definition.

If a test suite has an `init`, or stored properties, then the test functions should go in a separate extension block.

Test helpers, including static properties, always go in separate extension blocks, at the end of a file.


### Asserting behaviors

There are many ways to write the same test, but some patterns are more fluent than others. In particular, using the right patterns can help reduce the number of instances of `Issue.record` that appear in a test case.

#### Using `#require`

The `#require` macro can be used to unwrap optionals. However, direct comparison via optional-chaining is often more concise, and preferred when possible.

```swift
#expect(parsed?.count == expected)
```

#### Extracting case payloads

Use optionals to store extracted enum case payloads, and run comparisons against the optional values.

```swift
let value: UInt64?
if  case .uint64(let uint64)? = magnitude {
    value = uint64
} else {
    value = nil
}

#expect(value == expected)
```
